# REVIEW.md

Here is my review of the starter code in `app/main.py`. I walked through the helper calculations, input validation, concurrency guarantees, and pagination logic to identify bugs and behavioral defects against the OpenAPI contract and business rules.

| # | Where (function / line) | What is wrong | How you'd notice it (test, input, or symptom) | How you fixed it |
|---|---|---|---|---|
| 1 | `compute_late_minutes` (lines 33–37) | Timezone mixup (replaces UTC punch-in hours with IST shift start); doesn't truncate seconds; grace period condition `int(diff/60) > 10` returns 0 for 10:01–10:59; breaks on overnight shifts when punching in past midnight. | Punch-in at 09:40:01 on a 09:30 shift returns 0 late minutes instead of 10. Overnight shift punch-in at 00:30 yields negative or wrong calendar day values. | Truncate instant to whole seconds, convert to IST, compute difference against IST shift start datetime on attendance date, and check `diff_seconds > 600` before dividing by 60 (`diff_seconds // 60`). |
| 2 | `compute_work_hours` (lines 40–42) | Uses standard Python `round()`, which applies banker's rounding (round-half-to-even) instead of the half-up rounding required by R4. Also misses whole-second instant truncation. | 9090 seconds of work (2.525 hours) rounds down to 2.52 instead of 2.53. | Truncate instants to whole seconds, compute `diff_seconds / 3600` using `Decimal`, and quantize with `ROUND_HALF_UP` to 2 decimal places. |
| 3 | `compute_overtime` (lines 44–48) | Missing the >= 30-minute threshold check (counts minor overtime like 10–15 mins which should be 0). Assumes shift end is always on `date_str`, breaking overnight shifts ending the next day. Causes naive/aware datetime comparison errors. | Punch-out at 18:45 on an 18:30 shift returns 15 minutes instead of 0. Overnight shifts raise a `TypeError` or produce invalid timestamps. | Advance shift end by 1 day for overnight shifts (`shift_end <= shift_start`), evaluate `diff_seconds >= 1800`, and return `diff_seconds // 60` or 0. |
| 4 | `health` (lines 72–74) | Returns a hardcoded 200 OK without verifying that MongoDB is actually up and responding. | If MongoDB is stopped, `/health` still returns 200 OK instead of the required 503 Service Unavailable. | Run `client.admin.command("ping")` and raise an `HTTPException(503)` if the ping fails. |
| 5 | `create_employee` (lines 78–85) | Check-then-insert race condition on `emp_code`; missing unique database index; lacks input validation (regex on `emp_code`, email format, `shift_start != shift_end`); returns `created_at` as ISO string instead of epoch milliseconds. | Concurrent create requests produce duplicate employees with identical `emp_code`. Equal shift times are accepted. Response fails client-side schema validation on `created_at`. | Created a unique index on `emp_code` at startup, catch `DuplicateKeyError` to return 409, added Pydantic validations, and serialize `created_at` to epoch milliseconds. |
| 6 | `list_employees` (lines 89–96) | Off-by-one pagination bug (`skip = page * page_size` skips the first page entirely); `total` uses `count_documents({})` which ignores the department filter; missing default sort by `emp_code` ascending. | Page 1 skips the first 20 employees. Filtering by department still reports the total count of all employees in the database. | Fixed skip formula to `(page - 1) * page_size`, set `total = count_documents(q)`, added `.sort("emp_code", 1)`, and added query parameter constraints. |
| 7 | `punch_in` (lines 99–122) | Check-then-insert race condition on `(emp_code, date)`; throws an unhandled 500 when an employee doesn't exist (`emp["shift_start"]`); uses local machine clock instead of IST; fails R1 overnight shift date attribution; appends unwanted `"id"` field; serializes datetime instead of epoch ms. | Concurrent punch-ins create duplicate attendance logs. Unknown employee crashes with 500 instead of 404. Punch-ins before 06:00 on overnight shifts assign the wrong calendar date. | Added compound unique index on `(emp_code, date)`, catch `DuplicateKeyError` to return 409, validate employee existence with 404, implement R1 IST overnight date attribution, remove `"id"`, and return epoch ms. |
| 8 | `list_attendance` (lines 124–150) | In-memory fetch (`list(find(q))`) and Python sorting causes high memory usage and latency on large collections (~100k docs); missing secondary tiebreaker sort by `emp_code` ascending; missing validation `date_from > date_to` (must return 422); returns unwanted `"id"` field; crashes on legacy docs missing `half_day` or `history`. | High memory pressure and slow queries under load. Querying with `date_from > date_to` returns 200 with an empty list instead of 422. Legacy records fail serialization. | Executed query with database-level `.sort([("date", -1), ("emp_code", 1)]).skip(skip).limit(page_size)`, added validation for date ranges, serialized epoch ms, and defaulted missing legacy fields. |

### Things examined and verified NOT to be defects:
- **Using PyMongo's synchronous client in FastAPI**: FastAPI runs standard synchronous route functions in an AnyIO worker threadpool, so database I/O does not block the event loop. PyMongo handles connection pooling out of the box.
- **No `id` / `_id` field in AttendanceRecord**: The OpenAPI schema and `DATA_MODEL.md` explicitly state that attendance records do not expose an ID; each record is identified by `(emp_code, date)`.
- **Storing dates and shift times as strings**: Dates (`YYYY-MM-DD`) and shift times (`HH:MM`) are strings on purpose in MongoDB to represent pure calendar values without timezone conversion issues.
